# Deploy / Publish

## The one rule that matters

**Stop and ask before pushing `master` when the push is build-relevant.** The
`docker-publish` GitHub Actions workflow builds and publishes
`ghcr.io/hellboundglory/nexus:latest` on a `master` push only when at least one
changed path can affect the image (Go or web source, `Dockerfile`,
`go.mod`/`go.sum`, the workflow itself). A **docs-only** push (`.ai/**`,
`*.md`, `README`, `docs/`, `.superpowers/`, `AGENTS.md`, `CLAUDE.md`,
gitignore/gitattributes) is skipped by the workflow's path filter and is *not*
outward-facing — it needs no deploy-pause. Treat a **build-relevant**
`git push origin master` as a deploy-with-confirmation, every time, even when a
merge was authorized. See [`agent-policy`](../meta/agent-policy.md).

Pushing a **feature branch** is never publishing. Only `master` can be.

## Steps

1. Merge the feature branch to `master` — only after its whole-branch review is
   clean and the user has said "merge".
2. **Ask before pushing `master` when the push is build-relevant.** That push
   runs `docker-publish` (no local Docker build needed) and publishes
   `ghcr.io/hellboundglory/nexus:latest`. A docs-only push is skipped by the
   workflow's path filter and publishes nothing.
3. The user pulls the image on their host and recreates the container:
   `docker compose pull && docker compose up -d` on
   [`where-things-live`](../knowledge/where-things-live.md)'s production host.

## Validation

- `gh run list` / `gh run view` to confirm `docker-publish` succeeded after the
  push (unless it coincides with a GitHub API outage, see
  [`github-surfaces-fail-independently`](../memory/lessons/github-surfaces-fail-independently.md)).
- Confirm the running image on the host with `GET /api/v1/system/status` — it
  returns `{"version":"<git sha>"}` and settles "did the fix deploy?" in one
  call (see `where-things-live`).

## Expected Outputs

- A published `ghcr.io/hellboundglory/nexus:latest` image.
- A **GitHub Release** for each image build (standing rule added 2026-08-04):
  every build-relevant `master` push that produces a new image also creates a
  release with an auto-generated changelog. See "GitHub Releases" below.

## GitHub Releases (standing rule)

Each new image build gets a **GitHub Release with an auto-generated changelog**.
The `docker-publish` workflow's `release` job runs after a successful
`build-and-push` on a build-relevant `master` push:

- **Version/tag:** the release is titled and displayed as `v<shortsha>` (e.g.
  `v659af60`), but its **git tag is the BARE short SHA** (`659af60`). The bare
  tag deliberately does not match the workflow's `tags: ["v*"]` trigger, so
  creating it does **not** re-trigger `docker-publish` — otherwise every code
  push would build the image twice. This is an immutable, outward-facing tag:
  once published it cannot be reused (see
  [`github-surfaces`](../memory/lessons/github-surfaces-fail-independently.md) and
  the release discipline).
- **Changelog:** generated by `.github/scripts/changelog.sh` from the commits
  since the previous release (or the push's own range for the first release),
  grouped by conventional-commit type (`feat`/`fix`/`docs`/`ci`/…) with a
  compare link. No manual changelog maintenance.
- **Trigger safety:** docs-only pushes never run the workflow, so they produce
  no image and no release. A forced build (`v*` tag push or `workflow_dispatch`)
  may not create a release (the job is gated to `push` to `master`); the
  same-SHA guard prevents duplicates on reruns.
- **Verify:** `gh release list` / `gh release view` to confirm the release was
  created after a pushed build.

## Working notes

- **The whole-branch review gate happens before merge.** Every feature is
  reviewed (sdd reviewers + one opus whole-branch review) and the user signs
  off on the merge before any push to `master` is considered.
- **Force a rebuild without any code change:** push a `v*` tag or use the
  `workflow_dispatch` button on the workflow — both build and push regardless of
  which paths changed.
- **Prod access method:** the fastest reliable way to read prod state is to ask
  the user for the `NEXUS_API_KEY` (it lives in the host's `NEXUS_API_KEY` env
  in their deployed `docker-compose`) and `curl` the `/api/v1/...` API. Browser
  automation against this LAN host has proved unreliable — see
  [`where-things-live`](../knowledge/where-things-live.md).
